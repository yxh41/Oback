## 微信「一次滑动双返回」根因再辨析 + 结构性加固（commit ef730c9）
- **用户关键纠正（重要调试方法论）**：此前建议「关掉微信分组插件验证双返回」是**无效测试**——分组插件 ON 才存在「主界面→分组列表→聊天」三层结构；关掉插件三层塌成两层，双返回的物理前提消失，故「关插件后不双返回」既不能证明是插件手势、也不能证明是系统原生手势，只是因为没了第三层。✅ 此纠正成立，已采纳。
- **正确隔离测试**（用户称测试不了）：插件保持 ON（三层在），只切 oback 对微信的开关——oback 关(微信拉黑)仍双返回→与 oback 无关(原生或插件)；oback 开→单返回→修复覆盖到了。
- **结构性加固（不依赖「对手是谁」）**：`ObackManager.m` `_linkNavPopGesturesInWindow:` 新增第二道防线——递归枚举窗口视图树里**所有 `UIScreenEdgePanGestureRecognizer`**（含越狱插件私有的边缘返回手势），统一 `requireGestureRecognizerToFail:我们的 pan`。第一道仍是关掉 nav 原生 `interactivePop`。
  - 安全性：只碰 `UIScreenEdgePanGestureRecognizer`，**不动滚动用的普通 `UIPanGestureRecognizer`**；我们的 pan 是 `UIPanGestureRecognizer` 子类，被 isKindOfClass 过滤天然排除；视图树递归加 `depth>40` 护栏防爆栈。
  - 效果：无论对手是系统原生还是插件私有边缘手势，同一根手指只认 Oback 单次 pop，双返回从结构上不可能发生（含插件场景）。
- 推送：`76798c8..ef730c9 main -> main`，CI 应出 `0.1.0+ef730c9`。
- **待验证**：装 `0.1.0+ef730c9`，微信分组插件保持开，聊天界面左边缘滑一次应只回一层（聊天→分组列表），需再滑一次才到主界面。若仍双返回，则可能是插件用**非边缘手势**做返回(普通 pan/自定义)，届时需另寻方案(如枚举所有 pan 但需排除滚动——风险更高，先不碰)。

## 用户实测加固后仍双返回 → 真因修正（重要：推翻上节「插件非边缘手势」猜测）
- **实测**：`ef730c9` 后仍双返回。用户问「还有没有别的原因」→ 重新读 `_linkNavPopGesturesInWindow:` 调用链，发现**真因在我的代码时机，而非插件手势**：
  - 链接只在 `windowBecameKey:` / `start`(+延迟1s) 时做**一次**（ObackManager.m:125/129/142/148/158）。
  - 微信「主界面→分组列表→聊天」是**同一 window 内 push**，window **不会再次变 key** → 分组容器 nav/边缘手势在初次链接之后才压入视图树 → 枚举时不在树里 → **从未被链接** → 加固对那个容器形同虚设。
  - 故双返回还在，最可能是「链接时机漏了后创建容器」，比我之前甩的「插件非边缘手势」更站得住、更该修。
- **根治方案（未做，用户说先不管）**：把链接从「window 变 key 一次性」改为「手势真正接管时实时补链」——在 `gestureRecognizerShouldBegin:` 判定 `shouldBegin=YES` 那一刻，对当前 topMost 所在 nav 再调一次 `_linkNavPopGesturesInWindow:`（幂等无害）。容器何时创建都能在滑动前被压住。一行调用、低风险。
- **方案本身绕不过的盲区（真·罕见情况）**：加固只枚举 `UIScreenEdgePanGestureRecognizer`、不碰普通 `UIPanGestureRecognizer`（怕误伤滚动）。若分组插件用普通 pan 做返回，则 `requireGestureRecognizerToFail:` 压不到——需枚举普通 pan 并加滚动白名单过滤，代价大、易误伤，目前不碰。
- **其他改法副作用审视（已告知用户）**：① `requireGestureRecognizerToFail` 成对依赖，极端下若 pan 卡未失败态会使原生/插件边缘手势永久不 begin（极低：pan 生命周期正常）；② `windowBecameKey` 每次遍历视图树，频繁切 window 的 App 有轻微开销（depth>40 护栏+轻量，可接受）；③ 调试日志关闭时 OBLog 首行 return 零开销；④ 快滑零位移兜底(3c985fa)极快蹭边缘会误返（设计权衡，用户认可）；⑤ 灵敏度滑块/动量投影阈值调太低会误触发（默认 400/0.30 合理）。

## 实时补链修复已落地（commit a62eded，根治双返回）
- **做法**：在 `gestureRecognizerShouldBegin:` 的 `shouldBegin=YES` 分支（haptic 之后、return YES 前）加一行 `[self _linkNavPopGesturesInWindow:win];`。
- **为什么来得及压住当次滑动**：`requireGestureRecognizerToFail:` 是成对依赖，系统**每个 touch 事件都重评估**；我们的 pan 在手指移动期间保持交互态(Changed)不会失败，故对方边缘手势整段被阻塞，只弹一层。依赖设一次即持久，后续滑动也生效。
- **性能/功耗/App 影响（用户明确询问，评估结论均为「可忽略/无损」）**：
  - 触发频率：仅 edge+可返回 时 `shouldBegin=YES` 才调一次，**一次滑动一次**，非每帧。
  - CPU：遍历窗口视图树(depth>40 护栏)，纯内存属性设置 + 加依赖，**无 IO/布局/绘制**，亚毫秒~几毫秒级。
  - 功耗：无后台任务/定时器/轮询，对电池无 measurable 影响。
  - 对 App：仅当**我们接管**时压制对方边缘手势；`shouldBegin=NO`(非边缘/不可返回/横向滚动让位)时对方 `requireGestureRecognizerToFail` 依赖不阻塞(我们的 pan 没 begin→对方正常 begin)，故 App 自有边缘手势功能**完全保留**；滚动用的普通 pan **不枚举**，横滑/滚动不受影响；成对依赖极端卡死风险极低(pan 生命周期正常)。
- 与既有 `windowBecameKey` 一次性链接互补不冲突（前者覆盖初次，后者兜底后创建容器）。
- 推送：`26d630d..a62eded main -> main`，CI 应出 `0.1.0+a62eded`。**待真机验证**：微信分组插件保持开，聊天界面左边缘滑一次应只回一层。

## 新增「双返回诊断」开关（commit 08fb8e9）
- **用户认可**：上一轮问「要不要顺便加诊断开关」，用户回「好的」→ 落地。
- **做法**：`Root.plist` 调试分组新增 `PSSwitchCell`「双返回诊断」(key=`doubleReturnDiag`，默认关)；`ObackPreferences.doubleReturnDiagEnabled` 读取；`ObackManager._linkNavPopGesturesInWindow:` 末尾调 `_diagLogEdgeGesturesInWindow:` —— 该函数在开关开启时枚举窗口视图树所有 `UIScreenEdgePanGestureRecognizer`，打印**精确类名 + 宿主视图类**（`diag[双返回]: window=.. | 边缘返回手势共 N → [...]`）。
- **判读**：原生系统手势恒为 `UIScreenEdgePanGestureRecognizer`；清单里**任何其它类名**即 App/插件私有边缘返回手势 → 若双返回仍在，对照多出来的类名即可定位「第二层」是谁。
- **节流 + 门控**：同一 window 每 2s 最多打一次（避免每次起滑刷屏，用 `kDiagLastLogKey` associated 时间戳）；输出走 `OBLog`，故**需同时开启「调试日志」**才可见；关闭零开销。
- 推送：`887282e..08fb8e9 main -> main`，CI 应出 `0.1.0+08fb8e9`。
