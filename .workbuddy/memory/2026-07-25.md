## 提交 79a7f05 — 根治冻结+残留（stopAnimation + 双重保险）

### 问题
用户反馈微信/华为健康边缘返回后：
1. 界面冻结（点不动）或延迟 1~2 秒才恢复
2. 左侧残留白色竖条（上一页 toView 未完全归位）
3. 华为健康有阴影/上一屏残留

### 根因分析（oback_debug(31).log）
- `forceFinish animating` → `forceComplete done` 之间延迟 1~2 秒（0.22s 动画绝不该这么久）
- `pauseAnimation` 只是暂停 pa，paused animator 仍"持有" layer 动画状态 → 与我们的 UIView 动画发生 Core Animation 冲突
- 冲突导致：
  1. UIView 动画 completion 被严重延迟甚至永不触发 → `completeTransition:` 迟迟不执行 → 导航控制器卡在"交互进行中"态 → 界面冻结
  2. toView 的 transform 未正确动画到 identity → 左侧露出空白（window 背景色）→ 白色竖条残留

### 修复内容（ObackTransition.m `forceFinishIfNeeded`）
1. **`pauseAnimation` → `stopAnimation:YES` + release + nil**
   - 彻底释放 pa 对 layer 属性的控制，消除 CA 冲突
2. **移除 `fromView.alpha = 0.0` 淡出**
   - fromView 应该滑出屏幕（transform），不是淡出；淡出会掩盖真正的位移问题
3. **移除 `UIViewAnimationOptionBeginFromCurrentState`**
   - `stopAnimation:YES` 已把 presentation 值同步到 model，无需此选项
4. **completion + `dispatch_after(0.3s)` 双重保险**
   - completion 正常做 cleanup 和 `completeTransition:`
   - 0.3s 后若 completion 仍未触发，强制调用 `completeTransition:` + cleanup
   - `__block BOOL transitionFinished` 防止重复调用
5. **两边路径都显式清理 dim views + layer.cornerRadius/masksToBounds**
   - 避免任何残留

### 待验证
- 微信边缘返回是否流畅、无冻结
- 华为健康是否无阴影/上一屏残留
- 左侧白色竖条是否消失

## 提交 8445576 — 修复华为健康按钮空白 + 微信体验优化

### 问题
- 华为健康边缘返回后，底部功能入口按钮（健康管理、体重管理等）图标空白/看不到
- 微信边缘返回体验仍不理想（completion 偶有 1~2s 延迟，dispatch_after 保险路径偶尔触发）

### 根因分析（oback_debug(32).log + 代码审查）
`stopAnimation:YES` 会把 property animator 管理的所有属性恢复到 **pre-animation values**（动画开始前的值）：
- `toView.transform` 的 pre-animation value = `OBApplyParallax(0)` 的状态 = **缩放 0.92 + 偏移**
- `dim.alpha` 的 pre-animation value = **0.35**（dimAlpha）

这意味着 `stopAnimation:YES` 被调用时：
1. **toView 会从当前拖动进度（如 percent=0.47，scale≈0.96）突然跳回到 scale=0.92 的初始态**，然后 UIView 动画再把它拉回 identity。这个视觉跳跃对某些 App（如华为健康，可能使用复杂渲染/自定义 layout）会导致渲染损坏或 layout 计算错误 → **按钮图标空白**。
2. **`dim.alpha` 从 0 突然跳到 0.35**，导致遮罩闪一下。
3. CA 的属性恢复操作本身可能阻塞主线程，导致 UIView 动画 completion 仍然延迟 → 微信体验不佳。

华为健康 completion 本身没有延迟（`forceComplete done` 即时触发），说明问题不是 completion 延迟，而是 **`stopAnimation:YES` 恢复属性时造成的瞬时状态错误**。

### 修复内容（ObackTransition.m `forceFinishIfNeeded`）
**`[_propertyAnimator stopAnimation:YES]` → `[_propertyAnimator stopAnimation:NO]`**

| 参数 | 行为 | 问题 |
|------|------|------|
| `YES` | 恢复属性到 pre-animation 值 | toView 跳回 scale 0.92，视觉跳跃 + 渲染/layout 异常 |
| `NO` | 保持属性在当前值 | 从当前中间态平滑动画到终态，无跳跃 |

- `NO` 让 toView 保持在当前 `fractionComplete` 对应的 transform 状态（如 scale=0.96），UIView 动画从此状态平滑过渡到 identity。
- 消除属性跳跃，修复华为健康按钮空白。
- 减少 CA 属性恢复的主线程开销，改善微信 completion 延迟。

### 待验证
- 华为健康返回后底部按钮图标是否正常显示
- 微信返回是否更跟手、dispatch_after 保险路径是否不再触发
- 返回动画是否平滑自然（无突兀跳跃）

## 提交 413d732 — 根治底部空白 + 朋友圈等横向滚动界面无法触发

### 三个独立问题（oback_debug(34).log）

**问题 A：华为健康/微信底部空白（stopAnimation:NO 未根治）**
- 根因：`parallaxToView=YES`（nav pop）时给 `toView`（上一页）加 `scale` 视差（0.92→1.0）。
  上一页内部若含 `UIScrollView`，superview 的 `scale` transform 会破坏其 `contentOffset`/layout
  计算 → 转场结束后底部按钮区域被滚出/错位（华为健康底部功能入口空白）。
- 华为健康页面是 scrollView，受影响明显；微信页面结构不同受影响较轻。
- `stopAnimation:NO` 减轻了属性跳跃，但**转场过程中** toView 被缩放的瞬间已伤到 scrollView。

**问题 B：微信偶发底部空白（dispatch_after 路径）**
- 日志 line 498/962 走 `forceComplete done (dispatch_after)`，UIView 动画未完成时强制
  `completeTransition:`，此时 `toView.transform` 仍停留缩放态（非 identity）→ 收尾后残留。

**问题 C：朋友圈等界面无法触发**
- 朋友圈详情是**全屏横向 scrollView**（左右切上/下条）。其 `panGestureRecognizer` 优先级高于
  我们 window 上的 `ObackPanGestureRecognizer`，且只是 `UIPanGestureRecognizer`（非
  `UIScreenEdgePanGestureRecognizer`），没被 `linkNav` 的 `requireGestureRecognizerToFail` 覆盖
  → 边缘手势被系统取消，转场不触发。
- 日志无"让位横向滚动"/"不可返回"输出，说明是手势被 App 内部 scrollView 拦截（非我们逻辑 return NO）。

### 修复内容
1. **`OBApplyParallax` nav pop 分支**：上一页（toView）保持 `CGAffineTransformIdentity`（完全静止），
   去掉 scale/translate 视差（根本修复 scrollView 空白）。当前页（fromView）仍滑出+缩小（飞出感保留）。
2. **`forceFinishIfNeeded`**：completion 与 dispatch_after 两条路径，调 `completeTransition:` 前
   强制 `toView.transform = CGAffineTransformIdentity`（双保险，杜绝残留缩放态）。
3. **`ObackManager.linkNav`**：新增 `_enumerateHScrollPansInView:depth:block:` 枚举所有横向可滚动
   `UIScrollView`（`contentSize.width > bounds.width + 1`），对其 `panGestureRecognizer` 调
   `requireGestureRecognizerToFail:pan`（第三道防线）。边缘起滑时 ourPan 优先接管返回，
   中间横滑时 ourPan 不 begin 故放行给滚动。

### 权衡
- 去掉上一页"探出+放大"视差，上一页改为系统原生静止行为（OPPO 风格减弱，但稳定优先）。
- 若日后想加回视差，需只对非 scrollView 页面做，或对 scrollView 用不触发 layout 重算的方式。

### 待验证
- 华为健康返回后底部按钮图标是否正常（核心验证）
- 微信是否仍有偶发底部空白（dispatch_after 路径）
- 朋友圈详情页从最左边缘左滑是否能返回
- 从中间横向滑动朋友圈是否仍能正常切换上/下条（不被返回手势误拦截）

## 提交 ad81ee6 — 真正根治底部空白（上一轮 413d732 假设错误）

### 用户反馈（oback_debug(36).log）
"还是一样" —— 华为健康/微信底部按钮空白仍在。冻结已消失（所有 forceComplete done 秒级触发，dispatch_after 保险路径未再触发）。

### 关键纠正：413d732 的"toView scale 破坏 scrollView"假设是错的
- 代码确认 `OBApplyParallax` 的 nav pop 分支 `toView` 已是 `CGAffineTransformIdentity`，`fromView` 也只有平移无缩放 → 上一轮改动**生效但无效**。
- 空白还在 → 根因不是 toView 的 transform。

### 真正的根因（代码审查 `interruptibleAnimatorForTransition:` 第157行）
```objc
if (toView.superview != container) [container insertSubview:toView atIndex:0];
```
- 自定义转场中 UIKit **不会**自动把视图挂入 containerView，需 animator 自己加。
- 这行把**目的页(toView)从导航层级硬拽进 containerView，转场结束再拽回**。
- 目的页（华为健康首页/微信根页）底部 TabBar 常挂在 UIScrollView 或依赖 safeAreaInsets 布局；
  重挂载导致内部 `UIScrollView` 的 `safeAreaInsets`/`contentInset` 被重算 → 底部内容 `contentOffset`
  不回正 → 底部按钮区域被滚出视口 → 看起来"空白"。
- 与 toView 是否 transform **无关** → 所以去掉 scale 没用。也解释了微信"有时"才出现（取决于目的页底部是否含敏感 scrollView）。

### 修复（ObackTransition.m）
- nav pop（`parallaxToView=YES`）：**绝不把 toView 挂入 containerView**，只把 `fromView` 挂入做滑出。
  目的页本就在 container 下方原样可见，与**系统原生 pop 完全一致**（系统 pop 从不重挂载目的页）。
- 顺带移除 nav pop 的 dim 覆盖（目的页不被遮挡，也排除了 dim 干扰 TabBar 渲染的可能）。
- dim 仅保留给 modal dismiss（方案B），presenting 不 transform。
- `forceFinishIfNeeded`：completion / dispatch_after 两条路径都重置 `fromView.layer.shadowOpacity=0`（取消返回时 fromView 留在屏上，清掉永久投影）。
- 新增诊断日志 `toViewInContainer`（nav pop 应为 0）确认目的页从未被移动。

### 待验证（核心）
- 华为健康返回后底部功能入口按钮图标是否正常显示（最关键的验证点）
- 微信是否还出现底部空白
- 朋友圈详情页边缘左滑返回是否正常触发、中间横滑是否仍正常切条

### ⚠️ 实测（oback_debug(37).log）：ad81ee6 反而变成「整页空白」
- 用户反馈"这次返回后是空白页面了"——比底部空白更糟。
- 日志关键：`forceFinish animating ... toViewInContainer=0` → 目的页从未进 container。
- **根因纠正**：ad81ee6 把"挂入 toView"整行删掉是过度修正。自定义 nav-pop 转场里
  UIKit **不会**替你显示 toView，必须 animator 把 toView 呈现进 containerView，否则
  目的页永远不显示 → 整页空白。即"挂入"动作本身是必要的，底部空白的真正成因是
  **reparent 真实 toView（scrollView）导致 safeArea/contentInset 重算**，而非"挂入"这个动作。

## 提交 88dd6f0 — nav pop 用快照呈现底页（根治整页空白，同时保住底部空白修复）

### 思路
- 系统原生 pop 的底页本就完全静止 → 用 `snapshotViewAfterScreenUpdates:` 取一张
  像素级静态快照铺在 container 最底层作为"底页视觉"。
- 快照是离屏图片，reparent 它**永不伤真实 scrollView**（safeArea/contentInset 不被扰动）
  → 既修复整页空白（快照=底页视觉，真实 toView 一直待在导航层级底层没动），
  又根治底部空白（真实 toView 从不被挂载/不被重算）。
- `completeTransition` 后真实 toView 原样显露，零 layout 扰动、零空白、无闪烁。
- 兜底：快照取不到（极端情况）才回退到挂真实 toView，保证绝不 blank。
- nav pop 不创建 dim（底页不需压暗）。

## 提交 d3842e0 — 底部空白真正根治（快照时机错误→离屏渲染图像）+ 朋友圈修复

### 用户反馈（oback_debug(38).log）
"底部还是一样" + "微信朋友圈返回手势没效果" + "部分app无法进入app页面"。

### 🔑 决定性发现：88dd6f0 的快照方案**一次都没成功过**
- 日志**每次** nav pop 都打 `interruptible: nav pop 快照失败，退回到挂真实 toView`，
  且 `toViewInContainer=1`。
- 根因：`snapshotViewAfterScreenUpdates:NO` 在 `interruptibleAnimatorForTransition:`
  此刻 `toView` 尚未进窗口/未渲染 → 永远返回 nil → 每次都 fallback 把**真实 toView
  重挂载进 container** → 底部空白根因完全没动。所以 88dd6f0 实际等效于 ad81ee6 之前行为。

### 修复 1（底部空白真正根因）——离屏渲染底页图像
- 改用 `drawViewHierarchyInRect:afterScreenUpdates:YES` 强制离屏渲染 `toView` 当前内容
  成 `UIImage` → `UIImageView` 铺在 container 最底层。
- 该 API 不依赖 toView 是否进窗口，都能拿到正确像素（渲染的是 toView 自身子树内容）。
- 图像是静态离屏像素，reparent 它**永不伤真实 scrollView**（safeArea/contentInset 不被扰动）。
- `completeTransition` 后真实 `toView`（从头到尾没被移动）原样显露，零 layout 扰动、零空白。
- 兜底：图像为 nil 才回退挂真实 toView（等同旧行为，无回归风险）。
- 诊断日志改为 `nav pop 使用底页图像快照(避免底部空白)`，下一步真机验证此行应出现、
  `toViewInContainer` 应为 0。

### 修复 2（朋友圈无作用）——删"让位横向滚动"判断
- `gestureRecognizerShouldBegin` 里的"让位横向滚动"判断与 `_linkNavPopGesturesInWindow`
  的 `requireGestureRecognizerToFail` 链接**逻辑自相矛盾**：链接说"边缘我们赢"，
  shouldBegin 说"横向可滚就让步" → 两边互相卡死 → 朋友圈边缘返回从不 begin。
- 删除"让位"判断，统一由链接逻辑接管（边缘起滑 ourPan 优先返回，中间横滑 ourPan 不
  begin 故放行滚动）。朋友圈详情（横向 UIScrollView/UICollectionView pager）现可从边缘返回。

### 关于"部分app无法进入app页面"
- 假设 = 返回后目的页损坏/空白（与底部空白同根因），应随修复 1 一并解决。
- 若指"启动 App 后主页面打不开/空白"（与返回无关），需用户给具体 App + 日志另查。

### 待验证

- 微信：整页正常、无底部空白、朋友圈边缘可返回、中间横滑切条正常
- 部分 app 进不去页面是否消失（若是目的页损坏则应已解决）

## GitHub 同类项目调研（参考架构，解决现有+未来问题）

用户问"参考 GitHub 有没有类似项目可借鉴"。结论：**Oback 当前自定义转场 reparent toView 的架构本身是 bug 温床**，
所有成熟返回手势库都用"劫持系统原生 interactivePop"而非自写转场。

### 🔑 核心可借鉴技术：驱动系统原生 interactivePop 手势
取系统 `interactivePopGestureRecognizer._targets[0].target` + 私有 action
`handleNavigationTransition:`，把自己的（边缘）pan 挂到该手势的 view 上。
→ 系统原生 pop 转场运行，toView 由 UIKit 原生处理 → 彻底消除空白/导航栏损坏/scrollView 错位。
这是 FDFullscreenPopGesture / YLFullscreenSlider / BBGestureBack / PanCake 的共同做法。

### 参考项目清单
| 项目 | 亮点（可借鉴点） |
|------|------|
| **FDFullscreenPopGesture** (wangyingbo) | scrollView 同时识别模式 `gestureRecognizer:shouldRecognizeSimultaneouslyWithGestureRecognizer:` 在 `contentOffset.x<=0` 时返回 YES → 干净处理横向滚动 vs 返回冲突（朋友圈问题正解） |
| **YLFullscreenSlider** | 系统手势劫持 9 行核心代码；明确警告"根控制器触发返回会假死" → 手势须 `viewControllers.count<2` 时 NO |
| **BBGestureBack** (FKLam) | TabBar 磨砂布局错乱修复（iOS12+）；scrollView/tableView/CollectionView 同时识别；iPhone X 圆角风格参数 |
| **PanCake** (lwlsw) | **越狱插件**，全局手势注入 + 设置(灵敏度) + 键盘弹出禁用手势（防误触丢失输入）。最接近 Oback 的越狱全局场景 |
| **Protip blog + StackOverflow** | 自定义转场正确顺序：先 `[container addSubview:toView]` + `layoutIfNeeded` + `finalFrameForViewController:`，**再** `snapshotViewAfterScreenUpdates:YES`，最后动画快照（d3842e0 用错参数：NO 且没先 add） |

### 未来会遇到的坑（参考已踩过）+ 预防
1. **导航栏在快速交互 pop 时损坏** → transitionCoordinator 监控修复 nav bar layer 动画（dev59 已知 issue）。方案A(驱动系统手势)天然规避。
2. **根控制器触发返回→假死**（YLFullscreenSlider 明确警告）→ shouldBegin 里 `viewControllers.count<2` 直接 NO。
3. **scrollView 横向冲突**（朋友圈）→ 用 `shouldRecognizeSimultaneouslyWithGestureRecognizer:` 模式（FDFullscreenPopGesture），比 Oback 的 shouldBegin 让步判断健壮。
4. **键盘弹出误触返回丢输入** → PanCake 方案：键盘可见时禁用手势。
5. **TabBar 磨砂布局错乱**(iOS12+) → 方案A 规避；方案B 需额外处理。
6. **RTL 布局** → FMFullscreenPopGesture 支持。
7. **导航栏显示/隐藏切换转场**(with bar↔without bar) → FDFullscreenPopGesture view-controller-based 方案。

### 两个根治架构
- **方案 A（推荐，最稳）**：nav pop 改驱动系统原生 interactivePop（左右边缘都挂 pan 调 handleNavigationTransition:）。
  彻底消除当前所有空白/残留/冻结类问题，与社区十年经验一致。OPPO 强视差可先用边缘胶囊+系统视差顶着。
- **方案 B（保留 OPPO 强视差）**：保留 ObackAnimator，但修正快照顺序（见上 Protip/SO）：先 add toView→layoutIfNeeded→snapshotViewAfterScreenUpdates:YES→隐藏真实 toView 动画快照→收尾移除快照显真实 toView。

### 待决策
- 问用户：要我直接重构 nav pop 到方案 A（根治），还是保留 OPPO 强视差、先用方案 B 正确快照顺序修当前空白？

## 用户选定方案 A —— nav pop 重构为驱动系统原生 interactivePop（根治空白/残留/冻结）

### 决策（用户回复 "A"）
直接重构 nav pop 走系统原生 `interactivePopGestureRecognizer`，放弃自定义 `ObackAnimator` reparent 架构（空白/残留/冻结根因）。modal dismiss 仍保留方案B 自定义 `ObackAnimator`（只移 sheet 不碰 presenting，已验证无黑屏）。

### 实现要点（ObackManager.m + Tweak.xm）
1. **分流标志**：`gestureRecognizerShouldBegin:` 即设 `currentParallaxToView = (nav.childCount>1)` → 真=nav pop(系统原生) / 假=modal dismiss(方案B)。
2. **取系统私有 target**：`navPopSystemTargetForNav:` 读 `interactivePopGestureRecognizer._targets[0].target`（`_UINavigationInteractiveTransition` 实例）。
3. **手势 Began 即启动**：`beginTransition:`（interacting=YES 后）调 `driveSystemNavPopBeginWithPan:window:` → 把 window pan 作为 sender 喂 `handleNavigationTransition:` → 系统原生交互 pop 启动；`_transitionTriggered=YES`。
4. **update/end/abort 全程分流**：
   - `updateTransition:` nav 路径调 `_callSystemNavPop:`（scrub 进度），不再走 `interactive.updateWithPercent`（弃用自定义 `UIPercentDrivenInteractiveTransition`）。
   - `endTransition:` nav 路径把 Ended pan 喂 `handleNavigationTransition:` 后直接复位（不调 completeTransition / 无 watchdog，全由 UIKit 原生收尾）。
   - `abortTransition:` nav 路径同样喂 pan 让系统取消。
5. **delegate 返回 nil**：`ObackNavDelegate.animationControllerForOperation:...` 在 `operation==Pop && interacting` 时返回 nil → 系统用默认原生交互转场（toView 由 UIKit 原生呈现/清理，绝不进 containerView）。
6. **兜底**：取不到系统 target → 降级 `[nav popViewControllerAnimated:YES]`（interacting 置 NO 让 delegate 返回 nil → 系统默认转场），至少能返回不卡死。
7. **MRC 安全**：`_navPopTarget` 用 `assign`（非 `__weak`），无 ARC 违规。

### 关键不变量
- 系统 `interactivePopGestureRecognizer.enabled=NO`（setDelegate 时关），靠 `requireGestureRecognizerToFail:` 链接保证它先失败，绝不双重触发。
- nav pop 全程**无任何自定义转场/completeTransition/容器挂载** → 底部空白、导航栏损坏、scrollView 错位、冻结 全部从架构上消除。

## oback_debug(41) 分析 + 终极修复（commit 9d43dab，CI 出 0.1.0+9d43dab）
- 日志实锤：`[diag] pan touchesBegan` 到处有（cancelsTouchesInView=NO 生效，触摸送达）；但朋友圈 `WCTimeLineViewController` 只 `shouldBegin=YES`+`indicator shown`、**永无 `beginTransition`**；而 `WCCommentDetailViewControllerFB`/`ContactInfoViewController`（非列表详情页）正常 `beginTransition→navPop→commit=1`。
- **根因（列表页无返回）**：window 级普通 `UIPanGestureRecognizer` 在可滚动列表上被 `UIScrollView` 的 pan **抢赢识别**，即便用 `requireGestureRecognizerToFail` 让 scroll 失败于 ourPan 仍抢不过——这是普通 window pan 已知的老大难。规律：能返回=非列表页，不能=列表页。
- **终极修复**：弃用普通 pan，改用**屏幕边缘 pan** `UIScreenEdgePanGestureRecognizer`（左+右两个，基类 `ObackPanGestureRecognizer` 改继承它）。边缘 pan 自带「边缘优先于滚动」系统级优先级（=原生 interactivePop 在列表页能用的原理）。`gestureRecognizerShouldBegin:` 改按 `pan.edges` 判定方向、去掉 x 距离判定（边缘由系统判定）；`kPanKey` 改存 NSArray，链接/原生 interactivePop 失败于每个边缘 pan；枚举边缘手势时 `g.delegate==self` 跳过自身防自引用。
- **trade-off**：屏幕边缘 pan 的触发区为系统宽度（~13pt），`triggerWidth` 设置现仅作上限收紧（用户设更小值才生效，设更大无效）。可靠性优先；如需恢复 40pt 宽触发区再单独设计。
- marknow 黑名单（im.xym.marknow）本次仍生效（日志 SKIP attach/link）：装上此版若 marknow 能开→oback 注入是元凶（保留黑名单或深挖）；仍不开→与 oback 无关，可移除黑名单。
- MRC 合规（无 __weak），无遗留单 pan 引用。已 push `9d43dab`。待真机验证：朋友圈列表边缘返回/点详情、marknow 能否开、其它 app 返回与弹窗 dismiss 是否稳定。

## oback_debug(36) 分析 —— 朋友圈根因定位 + 修复方向
- (36) 实测（即 #144 / 5881738 构建）：微信内 oback 对**网页(HWH5ProWebViewController)与聊天(BaseMsgContentViewController via MMUINavigationController)正常返回**（shouldBegin→beginTransition→navPop 全链路），但**整份日志 WCTimeLineViewController（朋友圈）零 shouldBegin** → 朋友圈手势从未挂载/触发。
- 铁证：`attachNavPan` 列表里只有 SwiftUI/QQ/SG/通用 UINavigationController 及聊天 MMUINavigationController，**从无朋友圈的 nav**；且微信启动 `keyWindow=(null)`、首个 key window 是 `iConsoleWindow`(rootVC=nil)，真窗口是 `SHUIComponent.SHUWindow`。
- **根因（高置信）**：朋友圈所在 nav 不在 `win.rootViewController` 标准 `childViewControllers`/`presentedViewController` 链上（微信自定义容器），`_enumerateNavControllersFrom:` 与 `topMost:` 均只懂 UINavigationController/UITabBarController/presented 标准链 → **枚举遗漏** → nav.view 上无边缘 pan → 无胶囊无返回。这是 nav.view 方案（5881738）相比旧 window 级 pan 的回归：window 级时 topMost 偶能解析到 WCTimeLineViewController（41/42 日志可见 shouldBegin），挂 nav.view 后完全依赖枚举，反而丢了朋友圈。
- **修复方向（推荐「swizzle UINavigationController」）**：
  1. hook `UINavigationController` 基类 `viewDidLoad`（或 `initWithRootViewController:`+确保 view 加载），使其**任意子类（含微信 MMUINavigationController）一加载 view 即自动挂边缘 pan 到 nav.view**——绕过容器枚举，无论从哪个自定义容器进来都能挂载。
  2. `_attachNavPanToNav:win:` 里把**所属 nav 存为 pan 的关联对象**（kObackNavKey）；`gestureRecognizerShouldBegin:` 对 kind=nav 直接读 pan 所属 nav，**不再依赖 topMost 枚举** → 解析也根治。
  3. 同时 `nav.interactivePopGestureRecognizer.enabled=NO` + 失败于 ourPans（在 swizzle 里做，覆盖朋友圈 nav）。
  4. `_linkNavPopGesturesInWindow:` 的 scrollView 失败链接保留（视图树遍历，本就能覆盖朋友圈 scrollView）。
- **残余风险（诚实）**：若朋友圈压根不用 UINavigationController（纯自定义容器 swap view，无系统 interactivePop 可驱动），则 swizzle 也挂不到、方案A 模型无法 pop → 只能退回 Oback 自写转场（曾因空白/黑屏回退，风险高）。需用户开朋友圈左滑取**#144 干净日志**确认 WCTimeLineViewController 是否连 attachNavPan 都没有（几乎可确定无），再决定。
- 结论回应「朋友圈是不是解决不了」：**很可能可解**（swizzle 法），不是死局；唯一死局是朋友圈零 nav。下一步二选一：①直接实现 swizzle 修复推 CI 真机验；②先取 #144 朋友圈左滑干净日志 100% 确认理论。
