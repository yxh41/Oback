## 冻结复现分析 + 兜底修复 (d4ff196, 已 push)

**用户报告**：华为健康 + 微信"卡界面"（点不动、只能上滑回桌面）。附 `oback_debug(25).log`。

**日志实证关键差异**：
- 华为健康：转场正常走完 → 有 `animator done (cancelled=0)` → 不冻结（该次）。
- 微信：有 `oback-intc finish` + `animator spring applied` 但**无 `animator done`**；且 `interruptibleAnimatorForTransition:` 被**调用两次**（`interruptible ENTER` 出现两次，华为只一次）。

**根因定位**：中断式动画器交互转场里 `completeTransition:` **只**在 `UIViewPropertyAnimator` 的 completion 块调用。`finish` 靠 `continueAnimationWithTimingParameters:` 续跑动画器到底才触发 completion；但该 API 要求动画器处于 Active(paused) 态，微信"动画器被系统二次取用"导致状态错位 → `continueAnimation` **空操作** → 动画器永不到达 Stopped → `completeTransition` 永不调用 → nav 卡交互转场态 → 冻结。这跟 28fc77b 老 freeze（交互状态机没复位，`interacting` 卡 YES）**不是同一类**——`interacting` 每次都正常置 NO，是转场上下文"孤儿化"。

**修复（兜底强制收尾，根绝整类冻结）**：
- `ObackAnimator`：增 `context`(assign) / `completed`(BOOL) 属性 + `forceFinishIfNeeded`；completion 块加 `completed` 守卫防重复 completeTransition。
- `cancel`：在 `pa==nil` 早退**前**先置 `interactiveCancelled=YES`（否则兜底会以"提交"收尾误 pop）；并交 manager 兜底。
- `finish`：日志补 `pa.state` 便于真机定位状态错位。
- `ObackManager`：增 `_watchAnimator`(MRC 强引用) + `_scheduleCompletionWatchdog`：当前 ObackAnimator 0.8s 内若 `completed==NO`，由单例定时器(永不被释放，MRC 安全)强制 `completeTransition`。endTransition 快滑零位移分支仍走系统原生并提前 return（无 ObackAnimator 无需兜底）。

**为什么用单例定时器不是野指针**：manager 单例常驻；`_watchAnimator` 在定时器期间 retain 动画器，回调里 release。`forceFinishIfNeeded` 与动画器自身 completion 靠 `completed` 互斥，绝不重复 completeTransition。

**待真机验证**（`0.1.0+d4ff196`）：① 微信/华为边缘返回后界面不再冻结（最坏情况最多卡 0.8s 强制收尾）；② 留意日志 `oback-intc finish ... state=` 的 state 值——若微信侧 state 仍为 Inactive，即坐实"continueAnimation 空操作"假设，可考虑在 animateTransition 里主动 `pauseAnimation` 进一步根治（当前兜底已足够消除冻结感知）。
