## nav 视差「稳定版重构」（驱动机制变更）
- **根因**：navParallax 开关开启时，`beginTransition` 无条件调 `driveSystemNavPopBeginWithPan:`（系统私有 `handleNavigationTransition:` 启动原生交互 pop，并取 `_navPopTarget`），同时 `updateTransition` 的 navParallax 分支又调 `self.interactive updateWithPercent:`（自定义 animator scrub）。两套驱动源（系统 `_UINavigationInteractiveTransition` + 自定义 `ObackInteractiveTransition`）打架 → 个别 App 冻结/空白，这正是「视差实验」长期不稳的根因。
- **改动（ObackManager.m 两处）**：
  1. `beginTransition`：`if (currentParallaxToView)` → `if (currentParallaxToView && ![ObackPreferences navParallaxEnabled])` 才调 drive（方案A）。开启时 Began 不启动系统原生。
  2. `triggerTransitionInWindow:` nav 分支：`if (self.interacting)` → `if (self.interacting && _navPopTarget)` 才忽略重复 pop；否则 `popViewControllerAnimated:YES` 启动转场（开启时 _navPopTarget 恒 nil → 走此分支；方案A 时 _navPopTarget 非 nil → 忽略，不二次转场）。
- **复用**：开启路径现在走纯自定义 `ObackAnimator`+`ObackInteractiveTransition`（直接驱动中断式动画器 + `forceFinishIfNeeded` 双保险收尾），与 modal 方案B 同一套已验证稳的代码，单驱动无双源打架。
- **零回归**：默认(关)路径完全不变（仍方案A 系统原生 + nav pop 看门狗兜底 Filza 冻结）；灵敏度滑块此前对 nav 方案A 不生效（系统判定），重构后仅对「开启视差」路径生效（自定义判定），默认用户不动。
- **未删**：`driveSystemNavPopBeginWithPan:`/`_callSystemNavPop:`/`navPopSystemTargetForNav:`/`_scheduleNavPopWatchdog:` 保留给方案A。

## 【用户新报：main(9bf479e) 微信双返回 + 右侧返回体验差】

- **双返回根因定位(代码层面)**：main 的 `_linkNavPopGesturesInWindow:`(ObackManager.m 299–358)对**非排除** nav 做了三道防线——① `nav.interactivePopGestureRecognizer.enabled = NO`(337)+`failOnOurPans`(338)；② 枚举所有 `UIScreenEdgePanGestureRecognizer` 让其 failOnOurPans(343–347)；③ 枚举 scrollView pan failOnOurPans(351–354)。排除名单(`_isExcludedNav`)**仅微信朋友圈 WCTimeLine**，故微信主会话 nav 不在排除，理论上原生 interactivePop 被关。但：`requireGestureRecognizerToFail:` 是成对依赖，若微信(或越狱插件如"微信分组")的原生/私有边缘手势 **delegate 覆写 `shouldRequireFailureOfGestureRecognizer:` 返回 NO**、或 **事后把 interactivePopGestureRecognizer.enabled 重新置 YES / 重建手势实例**，则 ① 的禁用与 ② 的失败依赖失效 → 一次滑动同时触发"我们的 pan 驱动的 handleNavigationTransition:" + "微信原生/插件边缘手势" = **双返回**。
